The behavior you’re seeing matches how this repo is built: **local “with Supabase”** and **Vercel “without Supabase env”** are intentionally two different modes, even on the same branch.

## Most likely cause: Supabase env vars missing on Vercel (or not in the build)

Sign in / Sign up only render when both public Supabase variables are set at **build time**:

```1:6:src/lib/supabase/config.ts
/** True when both public Supabase env vars are set (build-safe: no throw). */
export function isSupabaseConfigured(): boolean {
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const key = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY;
  return Boolean(url && url.length > 0 && key && key.length > 0);
}
```

The header panel hides completely when that’s false:

```15:19:src/components/StudioAuthPanel.tsx
  const { configured, loading, user, signOut } = useSupabaseAuth();

  if (!configured) {
    return null;
  }
```

Locally you almost certainly have those in **`.env.local`**, which **never goes to Vercel**. On the cloud app you must set the same names in **Vercel → Project → Settings → Environment Variables** (see `docs/SUPABASE.md` and step 6 in `docs/DEPLOY.md`, where Supabase is listed as optional).

Without them, the app stays in **demo mode**: no sign-in UI, browser `localStorage` library, generation allowed without login — exactly what the docs describe.

### Next.js detail that trips people up

`NEXT_PUBLIC_*` values are **baked into the client bundle when Vercel runs `next build`**, not read fresh on every page load.

So if you:

- added the vars **after** the last deploy, or  
- set them only for **Preview** but you’re opening the **Production** URL (or the opposite),

the live site can still behave like “no Supabase” until you **trigger a new deployment** after the vars are correct for that environment.

**Quick check:** open `https://your-app.vercel.app/login`. If you see *“Supabase is not configured in this environment…”* instead of the form, that confirms missing/wrong build-time env — not a random UI bug.

## Second common cause: not the same deployment as your Dev branch

“Same code” locally vs on Vercel often isn’t the same **commit** or **branch**:

- Vercel’s **Production Branch** is often `main`, while you run `dev` locally.  
- A deploy can be from an older commit if push didn’t happen or the deployment failed.  
- **Preview** URLs (per-branch) vs **production** URL can differ if only one was redeployed.

Compare the commit SHA on the Vercel deployment with your local `dev` HEAD. If they differ, UI/auth changes from the last hour won’t match.

## What to verify (no code changes)

Branch/commit mismatch is the next thing to check if env is already set and you redeployed.
