## Issue found and fixed

**Library grid autoplaying every video**  
Each card used `PreviewVideo` with autoplay. With many clips (up to 48), that meant many simultaneous decoders, battery drain, and conflict with the “still in grids” pattern used by `MediaPreview`.

**Fix applied:**
- `PreviewVideo` now accepts `autoplay` (default `true` for hero/result).
- Library cards use `autoplay={false}` plus a Pexels **poster** from `demoVideoPosterForOutputUrl()` so cards stay still (including `prefers-reduced-motion` when a poster exists).

Video composer **result** still autoplays (intended preview behavior).

## Remaining edge cases (known, not blocking Phase 6)

1. **Stale library copy** — Cards still say *“Full recipe and remix arrive in Phase 5.”* Product/marketing already promises remix; that is Phase 5 scope, not a Phase 6 regression.

2. **No remix into Video** — There is no library → `/video?…` handoff yet. Video recipes are stored but not reloadable into the composer until Phase 5 (or a small follow-up).

3. **Effects → Video** — Presets only open the **image** composer by design. Video is blank composer only.

4. **Stored recipe validation** — `parseLibraryJson` does not check that `aspectRatio` is one of the allowed values. Bad/manual `localStorage` data gets a safe CSS fallback (`aspect-square` default), same as before Phase 6.

5. **`PreviewVideo` + reduced motion, no poster** — On the **composer result** (no poster passed), reduced-motion users still get a non-autoplaying `<video>` with `preload="metadata"`, not a still. Acceptable for now; posters could be wired there too if you want parity.

6. **External clip failures** — If a Pexels URL 404s or is blocked, there is no inline error UI (same class of issue as demo images).

7. **README status table** — Still lists early phases as “not started”; docs drift only, not runtime.

8. **Shared request parser** — Video API accepts image model ids (e.g. `soul-v2-standard`). Harmless; only affects the fallback warning flag.
